# Upgrade to 0.8.2

0.8.2 is a security and release-integrity hardening release. It does not intentionally change the user-facing domain model, but it **does add database objects and deployment requirements**.

## Before deployment

1. Back up the target database and verify the backup.
2. Deploy with the exact `pnpm-lock.yaml` committed with this release.
3. Configure the object-storage and trusted-proxy variables described below before starting the Web process.
4. Stop or drain SCIM provisioning traffic while the database migration is applied.
5. Run the privileged migration/setup workflow, then the restricted Web-role production checks.

## Database migration

Apply the normal migration pipeline. Migration `0037_final_release_hardening.sql` creates the Better Auth 1.7.3 SCIM runtime models used by the configured application-owned/static SCIM mode:

- `scim_connection_binding`
- `scim_identity_tombstone`
- `scim_subject`
- `scim_user`
- `scim_group`
- `scim_group_member`
- `scim_projection_grant`

It also creates `platform_operational_health`, a sanitized operational projection readable by the restricted Web role.

Existing pre-1.7 SCIM provisioning state is not compatible with the Better Auth 1.7 schema. Follow the Better Auth 1.7 SCIM cutover procedure: keep the old provisioner stopped during the cutover, remove/retire incompatible legacy plugin state as applicable, then perform a complete directory reprovision after the new schema is active.

## Object storage

Browser uploads now write only to a quarantine key. The worker scans the exact uploaded bytes and publishes them under a content-addressed server-only object key. A stale browser PUT URL can therefore no longer overwrite an attachment that has already passed malware scanning.

Production Web configuration must provide:

```text
OBJECT_STORAGE_PROVIDER=s3-compatible
OBJECT_STORAGE_ENDPOINT=https://<internal-storage-endpoint>
OBJECT_STORAGE_PUBLIC_ENDPOINT=https://<browser-reachable-storage-endpoint>
OBJECT_STORAGE_BROWSER_ORIGIN=https://<actual-presigned-browser-origin>
OBJECT_STORAGE_BUCKET=<bucket>
OBJECT_STORAGE_ACCESS_KEY_ID=<access-key>
OBJECT_STORAGE_SECRET_ACCESS_KEY=<secret>
OBJECT_STORAGE_REGION=<region>
OBJECT_STORAGE_PATH_STYLE=true|false
OBJECT_STORAGE_TIMEOUT_MS=15000
OBJECT_STORAGE_MAX_READ_BYTES=115343360
```

The public endpoint must be HTTPS outside local development and must have CORS rules that allow the application origin and the signed `PUT`/`GET` operations actually used by the application. Set `OBJECT_STORAGE_BROWSER_ORIGIN` to the exact origin that appears in presigned browser URLs (for virtual-hosted style this is normally `https://<bucket>.<public-host>`). CSP `connect-src` is generated from that exact browser origin.

## Reverse proxy

Set `TRUSTED_PROXY_HOPS` to the exact number of trusted reverse-proxy/load-balancer hops in front of the Web process. Do not expose the Web process directly to untrusted clients while also trusting forwarded client-address headers.

## Antivirus / scanner

Where document uploads are enabled, configure the scanner endpoint and timeout contract in the operations/worker environment. The scanner is fail-closed for the document availability transition.

## Release certification

On the supported Linux release workstation:

```bash
pnpm release:prepare
pnpm release:audit
pnpm source:package
```

`release:audit` is the runtime certification step. The source archive itself can be statically inspected on any platform, but production approval still requires the locked install, database migration/RLS/privilege checks, integration suite and E2E gates to pass for the exact release commit.
